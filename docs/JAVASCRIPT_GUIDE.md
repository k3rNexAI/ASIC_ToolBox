# JavaScript в ASIC ToolBox: путеводитель для начинающих

Это руководство объясняет, какие JavaScript-файлы есть в проекте и как выбор протокола проходит от интерфейса до ASIC и обратно. Имена ниже сверены с исходниками проекта. Пометки **Подтверждено кодом** означают, что это прямо следует из реализации; **Не следует предполагать** выделяет то, чего код не обещает.

## 1. Карта JavaScript-файлов

Упрощённо проект разделён на три зоны:

- **Корень проекта** — сервер и общие модули: Node.js читает файлы, отвечает браузеру и общается с ASIC.
- **`public/`** — код браузерных страниц: показывает формы, реагирует на действия и отправляет HTTP-запросы.
- **`test/`** — автоматические проверки отдельных общих модулей; это не код рабочего интерфейса.

### Базовые слова

- **Браузерный JavaScript** — код, исполняемый внутри открытой страницы. Он видит DOM (элементы страницы), реагирует на нажатия и использует `fetch()` для связи с сервером. В проекте это, например, `public/app.js` и `public/maps.js`.
- **Сервер Node.js** — JavaScript-процесс вне браузера. В данном проекте `server.js` слушает локальный HTTP-порт и может работать с файлами, сетью и дочерним процессом `grpcurl`.
- **HTTP API** — набор адресов, по которым клиент и сервер обмениваются запросами и ответами. Например, `POST /api/scan` запускает одиночное сканирование ЦОДа.
- **JSON** — текстовый формат объектов и массивов, используемый в теле HTTP-запроса/ответа. В JavaScript объект превращают в текст через `JSON.stringify()`, а ответ читают через `response.json()`.
- **`async` / `await`** — синтаксис для операций, результат которых появится позже (например, сетевого запроса). `await fetch(...)` ждёт ответ, не блокируя всю страницу целиком; `async` помечает функцию, которая возвращает Promise.
- **Событие** — сигнал о действии или изменении. Например, обработчик `.onchange` реагирует на изменение флажка, а `scanner-settings-applied` сообщает другим частям страницы, что настройки загружены или применены.

## 2. Откуда берутся протоколы и настройки

### Два разных выбора

На главной странице есть **настройка по умолчанию** и **выбор для текущего скана** — это не одно и то же.

1. В раскрываемой форме **«Настройки сканирования»** поле **«Протокол по умолчанию»** — `<select id="mapProtocol">`. Список включает `hybrid`, `rest`, `auto`, `grpc`, `legacy`.
2. В блоке **«ПРОТОКОЛ СКАНИРОВАНИЯ»** главной страницы находятся флажки `#useRest`, `#useGrpc`, `#useLegacy` с надписями REST API, gRPC и TCP. Именно они определяют протокол, который функция `selectedProtocol()` отправит при нажатии **«Сканировать ЦОД»**.
3. Форма общих настроек содержит кнопку **«Применить настройки»** (`#applyScanSettings`). Она сохраняет настройки по умолчанию, порты, таймауты и другие поля; флажки сканирования на главной — временный выбор текущего запроса.

В `public/scanner-settings.js` функция `fill(settings)` помещает ответ сервера в форму, записывает его также в `window.appliedScanSettings`, вызывает `syncProtocolControls(settings)` и рассылает событие `scanner-settings-applied`. Загрузка происходит GET-запросом к `/api/scanner-settings`; успешное применение формы — POST на тот же endpoint. Promise загрузки доступен через `window.scannerSettingsReady`.

На сервере:

- `defaultScannerSettings` в `server.js` начинает с `SCAN_PROTOCOL`, если это одно из допустимых значений; иначе default — `hybrid`. Другие значения могут задаваться переменными окружения, например `SCAN_CONCURRENCY`, `SCAN_MAX_IPS`, `REST_PORT`, `GRPC_PORT`, `LEGACY_PORT`, `ASIC_USER`, `ASIC_PASSWORD`.
- При старте `loadScannerSettings()` читает `scan-settings.json`. Если файла нет, остаются значения по умолчанию; после чтения параметры проходят через `normalizeScannerSettings()`.
- `GET /api/scanner-settings` возвращает `publicScannerSettings()`.
- `POST /api/scanner-settings` проверяет, что `protocol` содержится в `validScanProtocols`, проверяет числовые диапазоны и типы/длины прочих полей. Недопустимый протокол или поля дают HTTP 400. Проверенные значения записываются через `writeJsonAtomic()` в `scan-settings.json`; после этого настройки сразу обновляют `scannerSettings`, без перезапуска процесса.

**Подтверждено кодом:** сохранённый default действует для общего сканирования и служит fallback, когда сервер не получил допустимый протокол в запросе. На главной странице явный текущий выбор из флажков передаётся отдельно и может отличаться от default. Переключение флажка само по себе не вызывает POST `/api/scanner-settings` и не сохраняет его как default.

## 3. Трассировка: главная страница → сервер → ASIC → экран

### Шаг 1. Браузер решает, какой режим отправить

В `public/index.html` есть три флажка `useRest`, `useGrpc`, `useLegacy` и кнопка `scanBtn` с подписью **«Сканировать ЦОД»**. После восстановления настроек `syncProtocolControls()` устанавливает их начальное состояние по сохранённому протоколу: для `auto` включает все три; для одиночного режима отмечает соответствующий один; для `hybrid` отмечает legacy.

При клике обработчик `#scanBtn.onclick` в `public/app.js` сначала ждёт `window.scannerSettingsReady`, затем вызывает `selectedProtocol()`:

- ни одного флажка — `null`, запуск не выполняется;
- один REST — `rest`; один gRPC — `grpc`; один TCP — `legacy`;
- больше одного — `auto`;
- особый случай: только legacy при `window.appliedScanSettings?.protocol === 'hybrid'` даёт `hybrid`, а не `legacy`.

Затем `app.js` отправляет JSON с `{ codId, protocol }` запросом `POST /api/scan`. Обёртка `api()` делает `fetch()`, читает JSON и при `!res.ok` выбрасывает ошибку.

### Шаг 2. Сервер проверяет и готовит адреса

Обработчик `POST /api/scan` в `server.js`:

1. Не запускает второе сканирование параллельно со сканированием или мониторингом; при конфликте возвращает 409.
2. Читает JSON через `body(req)`, ищет ЦОД по `codId`; неизвестный ЦОД даёт 404.
3. Выбирает `protocol`: если `b.protocol` есть в `validScanProtocols`, берёт его; иначе берёт `scannerSettings.protocol`. В отличие от endpoint настроек, этот маршрут не отвечает 400 на неизвестный `b.protocol`, а использует default.
4. Читает сохранённую карту из `maps.json`, оставляет корректные уникальные IP. Если валидные IP карты есть, вызывает `scanIps(cod, mappedIps, protocol, ...)`; если нет — `scanCod(cod, protocol, ...)`, который разворачивает диапазон ЦОДа через `expandRange()`.
5. Проверяет лимит `scannerSettings.maxScanIps`, затем добавляет сводку `scanSummary()`, предложения `mixes()` и возвращает JSON.

### Шаг 3. `scanIps()` ведёт параллельный опрос

`scanIps()` в `server.js` удаляет повторные/невалидные адреса, проверяет лимит, создаёт до `scannerSettings.batchSize` работников (`worker`). Каждый вызывает `scanOne(ip, protocol, signal)`. Работники сохраняют позицию и результат по каждому адресу, а измеренное время добавляется как `responseTimeMs` и `scanDurationMs`.

`scanOne()` получает последовательность от `scanProtocolOrder()` из `miner-compat.js`:

| Значение `protocol` | Порядок, подтверждённый `scanProtocolOrder()` |
| ------------------- | --------------------------------------------- |
| `hybrid`            | `legacy`                                      |
| `auto`              | `rest`, затем `grpc`, затем `legacy`          |
| `rest`              | только `rest`                                 |
| `grpc`              | только `grpc`                                 |
| `legacy`            | только `legacy`                               |

`scanOne()` пробует режимы по очереди и возвращает результат первой успешной попытки. Ошибки попытки записываются; если все варианты провалились, `offlineDevice()` возвращает запись offline с причинами. При отмене (`AbortSignal`) отмена не выдаётся за offline.

### Шаг 4. Реальный вызов для каждого протокола

- **REST:** `restScanOne()` обращается к `/api/v1/auth/login` методом POST, получает token, затем параллельно запрашивает `/api/v1/miner/details`, `/api/v1/miner/hw/hashboards`, `/api/v1/miner/errors` и `/api/v1/cooling/state`. Результат приводит к общей записи с платами, состоянием, ошибками и вентиляторами.
- **gRPC:** `gRPCScanOne()` вызывает `grpcCall()` (внутри запускается `grpcurl`). Сначала `braiins.bos.v1.AuthenticationService/Login`, затем `braiins.bos.v1.MinerService/GetMinerDetails`, `.../GetHashboards`, `.../GetErrors` и `braiins.bos.v1.CoolingService/GetCoolingState`.
- **Legacy / TCP:** `scanOneLegacy()` запрашивает команды `version`, `summary`, `devs`, `devdetails`, `stats` через `apiCall()`, затем передаёт их в `normalizeCgminerResult()` из `miner-compat.js`. Именно `normalizeCgminerResult()` приводит разные формы CGMiner-ответов к общей записи устройства; `cgminerHashrateGh()` распознаёт разные единицы скорости, а `braiinsMinerState()` помогает интерпретировать состояние.

**Уточнение для `hybrid`:** первый массовый проход — только legacy/TCP, а не параллельные REST и TCP. После него `scanIps()` отбирает устройства, для которых `needsRestBoardDetails()` вернул `true` (онлайн, не sleep и не cgminer, подозрительное `0/3` или `check`), и делает REST-уточнение. Если REST недоступен, сохраняется первоначальный CGMiner-результат. При успешной REST-детализации Braiins также вызывается `attachNoPicMode()`.

**Уточнение для `auto`:** если REST или gRPC вернул Braiins-устройство не в `healthy`, а состояние майнера осталось `unknown`, `scanOne()` может дополнительно спросить legacy только для уточнения свидетельства SLEEP. Это не меняет общий fallback-порядок; по обычной попытке возвращается первый успешный протокол.

### Шаг 5. Ответ обновляет главную страницу

Сервер добавляет `protocol`, `scanSummary`, `mixes`, время и сведения о диапазоне/карте в ответ `POST /api/scan`. В `public/app.js` обработчик присваивает `data.devices` в `devices`, загружает сводку и миксы, затем вызывает `renderResults()`, `renderMixes()` и `renderRecipientControl()`. Обновляются таблица, счётчики и подпись последнего скана. После успеха или ошибки блок `finally` снимает состояние занятости с кнопки.

## 4. Главная страница и страница карт — различие

На `maps.html` подключены те же `public/scanner-settings.js` и общая панель настроек. Но `public/maps.js` запускает сканирование иначе:

1. `scan()` берёт отмеченные ЦОДы через `chosen()` и ждёт `window.scannerSettingsReady`.
2. Отображает сохранённый режим `window.appliedScanSettings?.protocol` как подпись.
3. Отправляет `POST /api/scan-all` с `{ codIds, demo }` — **protocol поле отсутствует**.
4. Обработчик `/api/scan-all` в `server.js` использует `b.protocol`, только если значение допустимо; иначе — `scannerSettings.protocol`. Следовательно, для этого вызова используется сохранённая общая настройка, а не временный выбор флажков главной страницы.
5. Результаты приходят в `data.results`; `maps.js` вызывает `loadMaps()`, `summary()` и `renderFleetMaps()`. Прогресс отдельно опрашивается GET `/api/scan-all/progress`.

В том же `public/app.js` есть отдельная функция `scanAllCods()`, которая отправляет `POST /api/scan-all` и, в отличие от `maps.js`, добавляет `protocol: selectedProtocol() || window.appliedScanSettings?.protocol || 'rest'`. Однако страница `maps.html` загружает `public/maps.js`, а не `public/app.js`. Поэтому не следует переносить поведение этого обработчика на кнопку **«Сканировать отмеченные»** в `maps.html`.

### Компактная схема потока

```text
Настройки: GET /api/scanner-settings → fill() → window.appliedScanSettings
                                      └→ syncProtocolControls() → флажки

Главная: флажки → selectedProtocol() → POST /api/scan {codId, protocol}
    → server.js: valid protocol? иначе scannerSettings.protocol
    → карта IP или диапазон → scanIps() → scanOne()
    → scanProtocolOrder() → REST / gRPC / legacy
    → общая запись устройств + scanSummary() + mixes()
    → JSON → devices/scanStats → renderResults() и соседние панели

Карты: сохранённые настройки → scan() → POST /api/scan-all {codIds, demo}
    → server.js берёт scannerSettings.protocol → scanIps() для каждого ЦОДа
    → JSON results → loadMaps() → renderFleetMaps()
```

### Два коротких сценария

- **Если на главной выбрали только gRPC →** `selectedProtocol()` вернёт `grpc`; `/api/scan` передаст его в `scanIps()`, `scanProtocolOrder('grpc')` вернёт только `['grpc']`, а `scanOne()` вызовет `gRPCScanOne()`. REST/legacy fallback не добавляется.
- **Если выбрали auto / включили два или три флажка →** главная отправит `protocol: 'auto'`; попытки пойдут REST → gRPC → legacy до первого успешного результата (кроме описанного уточняющего запроса состояния в особом случае).
- **Если default сохранён как hybrid, а на главной оставлен только TCP-флажок →** `selectedProtocol()` вернёт `hybrid`; быстрый проход будет через legacy/TCP, затем возможен REST для подходящих проблемных устройств.
- **Если на `maps.html` нажали «Сканировать отмеченные» при default `rest` →** `maps.js` protocol не отправляет; `/api/scan-all` возьмёт серверную сохранённую настройку `rest` для выбранных ЦОДов.

## 5. Как читать функцию

Удобно проверять функцию в таком порядке:

1. **Найти имя и входы.** Например, `scanOne(ip, protocol = 'rest', signal)` принимает IP, режим и сигнал отмены. Значение после `=` — значение по умолчанию при отсутствии аргумента.
2. **Посмотреть, что она вызывает.** `scanOne()` вызывает `scanProtocolOrder()` и одну из `restScanOne()`, `gRPCScanOne()` или `scanOneLegacy()`.
3. **Найти ветвление.** `if`, `?:`, `switch` и цикл отвечают за выбор пути. В `scanOne()` цикл означает переход к следующему протоколу при ошибке.
4. **Проверить результат.** `return` показывает, что функция отдаёт дальше. Например, `scanIps()` возвращает объект с `devices`, `scanSummary`, `protocol` и `mapIps`.
5. **Проследить вызывающего.** Найдите имя функции через поиск по проекту: так видно, кто создаёт аргументы и как использует результат.
6. **Отдельно прочитать `try/catch/finally`.** `catch` обрабатывает сбой, а `finally` выполняется и после успеха, и после ошибки. Это объясняет, почему UI сбрасывает блокировку кнопки.
7. **Не путать похожие уровни:** выбор интерфейса (`selectedProtocol()`), список порядка попыток (`scanProtocolOrder()`), сетевые функции (`restScanOne()` и другие) и форматирование результата (`normalizeCgminerResult()`) — разные задачи.

## 6. Словарь терминов из кода

- **API / endpoint** — конкретный адрес HTTP API, например `/api/scanner-settings` или `/api/scan-all`.
- **fallback** — запасная попытка после ошибки предыдущего способа. `auto` — явный последовательный fallback REST → gRPC → legacy.
- **legacy** — старый совместимый интерфейс CGMiner/BOSminer через TCP, в проекте обычно порт 4028.
- **`hybrid`** — специальная стратегия проекта: быстрый проход legacy, затем REST-детали для части проблемных устройств. Не равен `auto`.
- **Promise** — объект, представляющий результат, который появится позже; `async`-функции возвращают Promise.
- **`localStorage`** — браузерное хранилище для значений конкретного сайта. Например, `public/theme.js` сохраняет тему; настройки сканера сохраняет сервер в `scan-settings.json`, не `localStorage`.
- **DOM** — дерево HTML-элементов страницы, с которым работает браузерный JS: например, `document.querySelector('#scanBtn')` находит кнопку.
- **Сериализация** — превращение объекта JavaScript в текст JSON (`JSON.stringify`) для отправки по сети.
- **JSON-ответ** — данные, присланные сервером; клиент получает их через `response.json()` и обновляет интерфейс.
- **`AbortSignal` / отмена** — способ сообщить выполняющимся сетевым задачам, что сканирование нужно прекратить; сервер связан с кнопкой отмены через `/api/scan/cancel` или общий endpoint `/api/scan-all`.
- **Нормализация** — преобразование разных форм ответов прошивки к общей структуре. В коде для legacy это делает `normalizeCgminerResult()`.
- **Подтверждённый факт и предположение:** если цепочка не видна в коде, руководство не должно утверждать, что событие, сохранение или сетевой запрос обязательно происходит. Например, подпись «по умолчанию» не означает, что каждый запуск посылает настройку одинаковым способом: это проверяется отдельно для каждого обработчика страницы.

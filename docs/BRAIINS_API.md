# ASIC Mix Control — Braiins OS API и сеть

## Поддерживаемые протоколы

| Приоритет | API | Порт | Назначение |
|---:|---|---:|---|
| 1 | Braiins Public REST API | HTTP 80 | Основной быстрый путь; нативный Node.js HTTP-клиент и keep-alive |
| 2 | Braiins Public API gRPC | TCP 50051 | Резервный путь; `grpcurl` входит в комплект |
| 3 | BOSminer / CGMiner-compatible API | TCP 4028 | Совместимый legacy fallback |

Если выбран один переключатель, используется только соответствующий API. Если выбрано несколько, порядок fallback: REST → gRPC → TCP 4028. REST доступен в Braiins OS 25.07+ и подходит для прошивок 26.08+.

## REST API

Авторизация: `POST /api/v1/auth/login` с JSON `{ "username": "…", "password": "…" }`. Полученный `token` передаётся в заголовке `Authorization` последующих запросов. В пределах одного ASIC запросы сведений, hashboards и ошибок выполняются параллельно. HTTP keep-alive позволяет переиспользовать соединения и убирает накладные расходы на запуск отдельного процесса для каждого RPC.

Используемые endpoints:

- `GET /api/v1/miner/details` — модель, версия и сведения о майнере;
- `GET /api/v1/miner/hw/hashboards` — сведения о платах;
- `GET /api/v1/miner/errors` — диагностические ошибки, включая компонент и timestamp.

Ошибка чтения журнала не отменяет успешные данные майнера/плат: она выводится в журнал результата. Ошибка основных запросов вызывает fallback, если он включён.

## gRPC API

Используются `braiins.bos.v1.AuthenticationService/Login`, `MinerService/GetMinerDetails`, `MinerService/GetHashboards` и `MinerService/GetErrors`. Вызовы выполняются через включённый в комплект `grpcurl`.

## BOSminer / CGMiner-compatible API TCP 4028

Используемые команды: `version`, `devdetails`, `devs` и `edevs` (если поддерживается прошивкой). Последняя используется для дополнительной диагностики ошибок; доступность и формат ошибок зависят от реализации API.

## Скорость и достоверность

- Параллельность по умолчанию — 12 ASIC; допустимый диапазон настройки — 1–24 через `SCAN_CONCURRENCY`.
- Динамическая очередь не ждёт завершения всей партии перед запуском следующего устройства.
- Ответ каждого устройства содержит `scanDurationMs`; результат ЦОДа — `scanDurationMs` общего сканирования.
- Статус offline означает, что основные запросы выбранного API не завершились успешно (и резервные способы, если включены, тоже не сработали). Ошибка только диагностического endpoint сама по себе не делает устройство offline.


## Протокол сканирования карт и миксов

Основной сканер миксов и сканер карт используют общий серверный `scanOne`/`scanIps` pipeline. В интерфейсе карт REST API теперь доступен и выбран по умолчанию так же, как в основном инструменте. Режим `auto` пробует REST, затем gRPC, затем TCP 4028. Для чистого сравнения производительности выбирайте один протокол; режим `auto` предназначен прежде всего для совместимости, так как неудачные попытки увеличивают время ответа.


## Производительность: выбор протокола

REST выбран по умолчанию и в основном сканере миксов, и в разделе «Карты и результат». Резервные протоколы не запускаются автоматически без выбора режима `auto` (или выбора нескольких протоколов в основном интерфейсе): иначе неисправность REST-вызова могла добавлять до нескольких секунд ожидания перед fallback. Чтобы сравнить протоколы корректно, прогоняйте один и тот же набор IP сначала на `REST API`, затем отдельно на `gRPC` и `TCP 4028`. В таблице сканирования карт теперь показываются длительность сканирования и протокол для каждого ЦОДа. Параллельность по умолчанию остаётся 12 для сохранения проверенной точности.
